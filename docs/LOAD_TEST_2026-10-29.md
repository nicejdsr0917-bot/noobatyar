# Load test: directory endpoints, BEFORE (3aba241) vs AFTER (working tree at feb3607)

## Setup

- Machine: Mac laptop (Apple Silicon), `DEBUG=True`.
- Server: gunicorn with 4 `UvicornWorker` processes, bound to `127.0.0.1:8090`, `--timeout 60`.
- Database: PostgreSQL 16 (`postgres:16-alpine`) in Docker, running under amd64 emulation. Absolute numbers are pessimistic; compare the two versions relative to each other only.
- Postgres `max_connections` was raised from 100 to 400 (`ALTER SYSTEM`, container restarted) before the final runs. With the default of 100, the 4 workers exhausted connections (see "Errors").
- Throttles raised for the single load-generator IP: `THROTTLE_ANON`, `THROTTLE_USER`, `THROTTLE_PUBLIC_SLOTS`, `THROTTLE_OTP`, `THROTTLE_OTP_VERIFY`, `THROTTLE_LOGIN` all set to `100000/min`.
- Separate database per run (`nbbefore`, `nbafter`), same migrations, same seed.
- Load: Locust 2.34.0, `-u 200 -r 20 -t 60s`, one headless run per version, run one after the other.

## Seed size

- `seed_directory_demo`: 15 businesses plus the standard insurances.
- `import_directory` with a generated CSV of 400 Tehran businesses (source `loadtest`).
- Total: 415 public, approved businesses in each database.

## Workload

Each simulated user waits 0.5 to 1.5 s between tasks and collects business ids once at start:

| Task | Weight | Request |
|---|---|---|
| list | 5 | `GET /api/client/business/?page_size=20` |
| list | 1 | `GET /api/client/business/?page_size=100` |
| search | 2 | `GET /api/client/business/?search=کلینیک` |
| detail | 3 | `GET /api/client/business/<id>/` |
| slots | 2 | `GET /api/client/appointments/slots/<id>/?date=2026-11-05` |

The `[setup]` row is the single id-collection request made per user at start. It is counted in the aggregate.

## Reading the numbers

- Throughput differs by about 5% in favour of AFTER (48.65 vs 46.43 req/s), and median is about 200 ms lower. p95 is about 100 ms higher. The differences are within the run-to-run noise expected from one 60 s run on a laptop, so this does not establish a real improvement or regression. Repeat runs would be needed to call it.
- No endpoint failed in either version. Server logs for the final runs contain zero tracebacks.

## Caveats

- AFTER was measured from the live working tree of `Noobatyar-mobile-client/backend` at about 17:05 to 17:10 (local time). Per the reflog, HEAD was `feb3607` then, and commits `8b0f0e1` and `2fe9f2a` were made at 17:14, after the run. The working tree also had uncommitted backend changes; their state at run time was not recorded.
- BEFORE was a clean worktree at `3aba241`, removed after the run.
- Single run per version, 60 s each.

## Errors

- First BEFORE attempt, with `max_connections=100`: 798 tracebacks. The first distinct error was `psycopg2.OperationalError: ... FATAL: sorry, too many clients already`, 399 occurrences. That run was discarded; the numbers above come from the reruns after raising `max_connections` to 400.
- Final BEFORE and AFTER runs: 0 tracebacks, 0 failed requests.
