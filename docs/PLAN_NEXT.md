## قواعد کلی (برای همه مراحل)
1. **کاربر واقعی داریم:** مدل‌ها و سرویس‌های موجود را نشکن. فقط تغییر افزایشی: جدول/فیلد جدید (nullable یا با default)، API سازگار با نسخه‌های قدیمی اپ‌ها، migration بدون از دست رفتن داده. حذف یا تغییر نام فیلد ممنوع، مگر با مهاجرت مرحله‌ای.
2. **همه‌چیز تست دارد:** هر رویه (endpoint، flow اپ، صفحه وب) قبل از «تمام شد» تست خودکار دارد، حتی اگر هزاران تست لازم شود. باگی که پیدا می‌شود اول یک تست شکست‌خورده می‌گیرد، بعد رفع می‌شود.
3. **کارایی و مهندسی قبل از قابلیت‌ها:** مرحله P1 قبل از قابلیت‌های جدید (P2) انجام شود.
4. **دو اپ کاملاً جدا:** اپ اونر و اپ کلاینت دو محصول جدا هستند؛ فقط سرور مشترک دارند. نسخه، changelog، آپدیت اجباری و ریلیزشان جداست.
5. **وب و اپ جدا:** اپ کلاینت رزرو را داخل خودش انجام می‌دهد و سایت را باز نمی‌کند. اپ با برند نوبت‌یار است (نه رنگ کسب‌وکار)؛ رنگ کسب‌وکار فقط در وب.
6. **کجا کار کنیم:** کد یکپارچه روی برنچ `mobile-client` در worktree `../Noobatyar-mobile-client` است (develop + اپ کلاینت). بک‌اند محلی: preview `backend_mobile_client_mac`.

## P0 — باگ‌های جدی و امنیت داده (اول از همه)
1. **🐞 نشت پیام‌ها بین کسب‌وکارها:** کاربری که در چند کسب‌وکار نوبت گرفته، وقتی اونر پروفایلش را باز می‌کند، در تب «پیام‌ها» پیام‌های همه کسب‌وکارها را می‌بیند؛ باید فقط پیام‌های همان کسب‌وکار را ببیند.
   - مسیر: اپ اونر `data/repository/message/MessageRepositoryImpl.kt` → `VisitorApiService.getVisitorMessages(visitorId, businessId)` → بک‌اند `visitor/views.py` `VisitorMessageHistoryView` (فیلتر `business__user` + `business_id` اختیاری). Visitor سراسری است (یک ردیف برای هر شماره در کل پلتفرم).
   - اول باگ را بازتولید کن (اونر با چند کسب‌وکار / مشتری مشترک) و علت دقیق را پیدا کن: `business_id` غلط یا خالی از اپ؟ کش Room؟ اختیاری بودن `business_id` در بک‌اند؟ لاگ پوش؟
   - رفع: `business_id` اجباری و چک مالکیت در بک‌اند، و فیلتر درست در اپ.
2. **ممیزی جداسازی داده (multi-tenant):** همه endpointهای اونر (visitor، appointment، sms/push logs، stats، promo، …) یک تست «اونر A داده اونر B یا کسب‌وکار دیگرش را نمی‌بیند» داشته باشند. هر مورد نشت = P0.
3. **🔒 شماره کارت در API عمومی:** `api/client/business/` بدون ورود `card_number` و `card_owner_name` را برمی‌گرداند. فقط بعد از ثبت نوبت در checkout برگردانده شود.
4. **🐞 آمار «امروز» با UTC:** `appointment/views/appointment_stats_view.py:93` → `timezone.localtime(now)`؛ fixture تست `tests_daily_counts.py` هم با تاریخ محلی ساخته شود.
5. **🐞 بله بعد از تایید/رد مشخصات را پاک می‌کند:** `bale/views.py` `_finalise_message` کل متن را با «وضعیت — عنوان» عوض می‌کند؛ باید `build_text(...)` بماند و نتیجه و دلیل زیرش اضافه شود.
6. **🐞 merchant پیش‌فرض واقعی:** `core/settings.py` بدون `ZIBAL_MERCHANT_ID` یک merchant واقعی در کد دارد؛ در DEBUG پیش‌فرض باید `zibal` (تست) باشد.

## P1 — مهندسی، تست و کارایی (قبل از قابلیت‌های جدید)
1. **زیرساخت تست**
   - بک‌اند: هدف پوشش همه endpointها؛ تست قرارداد API (شکل پاسخ‌ها برای اپ‌های قدیمی)؛ تست جریان‌های پول (callback زیبال/مایکت، ledger)؛ `assertNumQueries` برای endpointهای پرترافیک.
   - اپ اونر و کلاینت: تست ViewModel/Repository در `commonTest` (با fake API)؛ چند تست UI برای مسیرهای اصلی.
   - وب: تست typecheck/lint + تست e2e (Playwright) برای پروفایل، رزرو، پرداخت.
   - CI: روی هر push، تست بک‌اند + تست KMP هر دو اپ + typecheck وب. (الان CI فقط ریلیز اندروید دارد.)
   - تست‌های ترتیبی: `manage.py test --parallel` با تست fail‌شده خطای pickle می‌دهد؛ پایدارش کن.
2. **کارایی**
   - ممیزی کویری‌ها (N+1، `select_related/prefetch_related`)، ایندکس‌های لازم (افزایشی)، صفحه‌بندی همه‌جا.
   - کش Redis برای لیست عمومی، جزییات کسب‌وکار، اسلات‌ها (با invalidation روی تغییر).
   - تنظیم workerهای gunicorn/uvicorn، `CONN_MAX_AGE`/pgbouncer، محدودیت thread pool برای `sync_to_async`.
   - ارسال پیامک/پوش بیرون از مسیر درخواست (صف کار؛ زیرساخت جدید مجاز است، تغییر مدل نه).
   - رسانه: سرو مستقیم با nginx، فشرده‌سازی و thumbnail.
   - load test (مثلاً locust) برای endpointهای اصلی با هدف p95 مشخص؛ نتایج را در `docs/` ثبت کن.
3. **مشاهده‌پذیری:** لاگ ساختاریافته، Sentry (یا معادل در دسترس از ایران)، slow query log، health check، تست بازیابی بکاپ.
4. **جدایی دو اپ**
   - `versions.AppVersion` فیلد `app` (OWNER/CLIENT) و در صورت نیاز `platform` بگیرد (افزایشی؛ پیش‌فرض OWNER برای ردیف‌های موجود). `version/check` با پارامتر app.
   - changelog جدا برای هر اپ؛ تگ CI جدا (مثلاً `v*` برای اونر، `client-v*` برای کلاینت)؛ آپدیت اجباری مستقل.

## P2 — قابلیت‌ها
### ۲.۱ رفع‌های کوچک
- **اپ اونر: لوگو اجباری** و بالای مرحله اول فرم (الان کسی نمی‌بیند).
- **گزارش تخلف در اپ کلاینت** سرتاسری کار کند (دیالوگ و endpoint `client/businesses/<id>/report/` هست؛ تست و رفع ثبت، داشبورد ادمین و بستن گزارش).

### ۲.۲ بک‌اند (همه افزایشی)
1. **منبع نوبت:** `Appointment.source` (WEB / APP / OWNER، پیش‌فرض برای قدیمی‌ها)، در API اونر و گزارش («این ماه X مشتری از اپ نوبت‌یار»).
2. **نمونه‌کارها:** عکس + توضیح + ترتیب؛ تایید ادمین قبل از نمایش (مثل لوگو، در صف بررسی و کارت بله).
3. **مدارک و افتخارات:** عنوان، صادرکننده، سال، عکس؛ تایید ادمین.
4. **نظرات:** هر کاربرِ ثبت‌نام‌کرده (مشتری) امتیاز ۱–۵ و متن؛ انتشار بلافاصله؛ گزارش نظر با همان سیستم ContentReport؛ حذف توسط ادمین؛ پوش Firebase به اونر برای نظر جدید.
5. **امتیاز رتبه‌بندی:** فیلد امتیاز + دستور cron شبانه (میانگین و تعداد نظرات، کامل بودن پروفایل: لوگو/نمونه‌کار/خدمات/شهر/پین، فعالیت، ضریب تبلیغاتی آینده)؛ ترتیب لیست کلاینت.
6. **بنرهای اونر:** چند بنر برای هر دسته کسب‌وکار؛ همه یک لینک مشترک (قابل تنظیم در ادمین) باز می‌کنند؛ در ادمین کنار هر دسته تعداد اونرها؛ ابعاد ۱۲۰۰×۴۰۰ در فرم نوشته و عکس با ابعاد غلط رد شود. برای همه اونرها نمایش داده می‌شود (فرض؛ لینک می‌تواند صفحه ارتقای پلن باشد).
7. **فهرست دستی مراکز برای بازاریابی:** ثبت دستی دکتر/سالن/… در ادمین با مشخصات، تلفن، آدرس، پین (همان `is_claimed=False`)؛ بخش پیگیری: وضعیت (تماس نگرفته/گرفته/علاقه‌مند/عضو شد/علاقه ندارد)، یادداشت هر تماس، تاریخ پیگیری بعدی، لیست «تماس‌های امروز».
8. **دو سرویس عمومی برای سایت noobatyar.ir:** «مشتری‌های فعال» (عضو با اشتراک فعال) و «جدیدترین کسب‌وکارها»؛ JSON با کش + یک تکه HTML آماده برای سایت.

### ۲.۳ اپ کلاینت
1. **بازطراحی صفحه کسب‌وکار** با برند نوبت‌یار: هدر، وضعیت باز/بسته، خدمات (chip)، نوار روزهای کاری، بیعانه و روش پرداخت، گالری نمونه‌کار، مدارک، خلاصه و لیست نظرات، نقشه، گزارش.
2. **رزرو نیتیو:** خدمت → روز و ساعت (available-slots) → ورود OTP (فقط بار اول) → تایید → بیعانه در درگاه → تب «نوبت‌های من»؛ `source=APP`.
3. **ثبت نظر و گزارش نظر.**
4. **امتیاز ویژه اعضا (علاوه بر تیک بنفش)** — هنوز انتخاب نشده؛ پیشنهادها: «اولین نوبت خالی» روی کارت لیست (پیشنهاد اصلی)، فیلتر «نوبت امروز»، «پیشنهاد ویژه اپ» که اونر تعریف می‌کند (مثلاً ۱۰٪ تخفیف رزرو از اپ). از کاربر بپرس.

### ۲.۴ اپ اونر
1. **نمونه‌کار و مدارک:** آپلود با cropper موجود + فشرده‌سازی مثل لوگو؛ نمونه‌کار ۱۰۸۰×۱۰۸۰، مدارک ۱۰۸۰×۱۳۵۰؛ هنگام نمایش، لوگوی نوبت‌یار گوشه هر عکس (برداشت از «کنارش عکس و لوگوی نوبت‌یار» — تایید کن).
2. **نظرات:** صفحه فقط‌خواندنی + نوتیف.
3. **نشان منبع روی هر نوبت.**
4. **بنر چرخشی (آلبومی) در صفحه اصلی** بر اساس دسته کسب‌وکار.

### ۲.۵ وب کلاینت
- بخش‌های نمونه‌کار، مدارک و نظرات در `b/[slug]`؛ `source=WEB` برای نوبت‌های سایت.

### ۲.۶ پنل ادمین
- بازچینی منو بر اساس کار روزانه (بررسی کسب‌وکارها، نظرات و گزارش‌ها، بنرها، بازاریابی، اشتراک و مالی، پیامک) با برچسب‌ها و راهنمای ساده تا یک آدم معمولی بتواند کار کند.
- صف بررسی عکس‌ها و نظرات، بنرها با راهنمای ابعاد، فهرست بازاریابی، نمای امتیاز رتبه‌بندی.
